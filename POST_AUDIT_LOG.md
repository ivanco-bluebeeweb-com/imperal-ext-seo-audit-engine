## 2026-08-20 — PST Часть D — НАЙДЕН И ИСПРАВЛЕН РЕАЛЬНЫЙ КРИТИЧЕСКИЙ БАГ: SSRF без защиты

**Что было не так.** `seoaudit/fetcher.py` — движок краулинга, единственный
в портфеле, чья основная функция — обходить произвольные пользовательские
домены по-настоящему по HTTP (`audit_sites` принимает любую строку от
пользователя). До этой правки `Fetcher.fetch()` не делал НИКАКОЙ проверки
резолвленного IP перед подключением — ни на первом запросе, ни на каждом
хопе ручного редиректа. Это значит: пользователь мог отправить на "аудит"
`127.0.0.1`, внутренний сервис за файрволом или облачный metadata-эндпоинт
`169.254.169.254` (AWS/GCP/Azure — отдаёт живые облачные креды кому угодно,
кто до него дотянется) — и краулер честно бы туда подключился.

**Почему это не было замечено раньше.** Все остальные приложения портфеля
либо вообще не делают исходящий fetch, либо целятся в фиксированный
провайдерский хост (константа вроде `NOTION_API`/`BASE_URL`), либо (как
Make.com) сознательно fetch'ат owner-настроенный webhook — принципиально
другой класс риска. SEO Audit Engine — единственное приложение, где целевой
адрес это буквально то, что назвал вызывающий, поэтому единственный
защитный слой должен был быть внутри самого fetcher'а, а его не было.

**Фикс.** Добавлена `_check_host_is_public(host)` в `seoaudit/fetcher.py`:
резолвит хост через `socket.getaddrinfo`, отказывает если ЛЮБОЙ из
резолвленных адресов (A/AAAA) приватный/loopback/link-local/reserved/
multicast/unspecified (через `ipaddress.ip_address(...).is_private` и
аналоги). Вызывается на КАЖДОМ хопе `Fetcher.fetch()`, включая редиректы —
редирект на внутренний адрес это тот же SSRF, только на шаг позже. Также
добавлена проверка схемы (только `http`/`https`) — блокирует
`file://`/`gopher://` и подобные попытки обхода через смену схемы.
Неразрешаемый хост трактуется как заблокированный (fail-closed), не
пропускается молча.

**Известный остаточный риск, задокументированный, не устранённый.** DNS
rebinding в узком окне между проверкой резолва и реальным `connect()`
внутри `urllib` этим фиксом не закрывается — для этого пришлось бы менять
транспорт urllib, чтобы "приколоть" уже проверенный IP к последующему
TLS-подключению, что выходит за рамки этого аудита. Задокументировано в
module docstring `fetcher.py` как явный trade-off.

**Тесты.** Новый файл `tests/test_fetcher_ssrf.py` — 14 тестов: прямые
unit-тесты на `_check_host_is_public` (loopback IP/hostname, cloud metadata,
private class A/C, IPv6 loopback/ULA, публичный IP не блокируется, порт не
обходит проверку, нерезолвящийся хост блокируется) плюс end-to-end тесты
через `Fetcher.fetch()` (loopback URL, metadata URL, non-http схема,
`fetch()` никогда не бросает исключение на заблокированном хосте — только
возвращает `ok=False`). Полный набор приложения: 217/217 зелёные (было 203).

**Занесено в `Docs/known-bug-patterns.md`** как системный паттерн: любой
будущий коннектор с реальным краулингом/fetch по адресу, ПРИДУМАННОМУ
пользователем (не фиксированному провайдерскому хосту), обязан резолвить и
проверять IP на каждом хопе, включая редиректы, прежде чем подключаться.
