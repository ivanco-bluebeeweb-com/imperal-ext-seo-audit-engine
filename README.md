# SEO Audit Engine

Технический SEO-аудит портфеля сайтов — и автоматические задачи по итогам.

Рассчитан на агентство с 20-200 сайтами. Замер на реальных сайтах:
**200 сайтов ≈ 11-22 минуты**, база ~37 МБ (см. «Масштаб» ниже).

---

## Главный принцип: аудит только читает

Движок **никогда ничего не меняет на сайтах**. Он судья, а не исполнитель:
обходит страницы, сравнивает с нормами, выносит находки и формирует задачи.

Правки вносит отдельный инструмент (`wp-site-connector`) — и только по
подтверждённой задаче. Разделение намеренное: аудит ходит по чужим сайтам,
и такому процессу незачем иметь права на запись.

Из этого следует правило, которое стоило отдельной отладки: **аудит не
судит то, чего не видел**. Если страница не загрузилась, про неё нельзя
сказать «нет заголовка» — только «неизвестно». Однажды из-за ошибки в
определении кодировки не скачалась ни одна страница сайта, а отчёт всё
равно выдал 35 уверенных находок. Теперь это невозможно: незагруженные
страницы отсеиваются, и на такой случай есть тест.

## Быстрый старт

```bash
# 1. список сайтов — по одному на строку
cat > sites.txt << 'EOF'
climtec.md
ksrenovationgroup.com
example.org
EOF

# 2. аудит
python3 -m seoaudit audit --sites sites.txt --db audit.db --max-pages 50

# 3. отчёты: по портфелю + по каждому сайту
python3 -m seoaudit report --db audit.db --out reports/

# 4. план выгрузки задач в трекер
python3 -m seoaudit export --db audit.db --json plan.json
```

Дальше — Webbee: «выгрузи план в Asana». Или в панели Imperal:
Приложения → SEO Audit Engine.

## Команды

| Команда | Что делает |
|---|---|
| `audit`  | обойти сайты и записать находки |
| `resume` | продолжить прерванный прогон с того же места |
| `report` | отчёты Markdown + JSON (по портфелю и по каждому сайту) |
| `tasks`  | показать задачи или выгрузить их в JSON |
| `export` | план выгрузки в трекер (разделы, сроки, теги, метки) |

Полезные ключи `audit`:

```
--max-pages N      сколько страниц на сайт (по умолчанию 50)
--site-workers N   сколько сайтов одновременно
--page-workers N   сколько страниц одновременно внутри сайта
--label "текст"    подпись прогона, чтобы отличать в истории
```

## Одна страница вместо всего сайта (`page_url`, opt-in)

`list_findings`, `list_tasks` и `get_report` понимают необязательный параметр
`page_url` — точный адрес ОДНОЙ страницы. Пусто (по умолчанию) — поведение
не меняется вообще: старая site-wide/portfolio-wide логика работает
байт-в-байт как раньше.

```
Webbee, покажи находки по Home странице g4s.md
→ list_findings(page_url="https://g4s.md/")

Webbee, отчёт по https://g4s.md/
→ get_report(page_url="https://g4s.md/")   # site можно не называть —
                                            # определится по хосту адреса
```

Как это работает:

- **Точное совпадение, без подмены.** Сравнение через ту же нормализацию
  URL, что судит canonical (регистр схемы/хоста, конечный слэш — не важны).
  Если такой страницы нет среди проверенных — явная ошибка со списком
  известных адресов сайта, а не тихий выбор «похожего» URL.
- **`site` можно не указывать**, если дан `page_url` — сайт определяется по
  хосту адреса. Если оба заданы и указывают на РАЗНЫЕ хосты — явная ошибка
  (не молчаливый выбор одного из двух).
- **Задачи и site-уровневые находки не теряются.** Находка уровня сайта
  (сироты, битые внутренние ссылки и т. п.) попадает в срез страницы, если
  эта страница упомянута внутри неё — с пометкой `matched_via="evidence"`,
  в отличие от `matched_via="url"` для находок именно этой страницы.
  Задача возвращается целиком (её `fingerprint` не меняется под срез) —
  повторный экспорт в трекер не создаёт дублей.

### В панели

Тот же `page_url`-слой стоит и за двумя экранами панели:

- **«Все страницы»** (открывается кнопкой «Все страницы» с карточки сайта) —
  список страниц сайта с переключателем «Все страницы» / «Только с
  находками». Клик по строке ведёт в карточку конкретной страницы.
- **«Карточка страницы»** — canonical, статус-код, находки именно этой
  страницы (с пометкой «своя находка» / «часть находки уровня сайта») и
  задачи, которые её касаются. Неизвестный адрес — честная ошибка со списком
  проверенных страниц, без подмены на похожий URL.

## Масштаб

Замер: 4 сайта × 25 страниц = 52 секунды при 4 потоках. Время определяется
самым медленным сайтом, поэтому счёт идёт «волнами».

| Сайтов | 8 потоков | 16 потоков | База |
|---:|---:|---:|---:|
| 20  | ~2 мин  | ~1 мин  | ~4 МБ |
| 50  | ~5 мин  | ~3 мин  | ~9 МБ |
| 100 | ~11 мин | ~5 мин  | ~18 МБ |
| 200 | ~22 мин | ~11 мин | ~37 МБ |

Рекомендации для 200 сайтов:

```bash
python3 -m seoaudit audit --sites sites.txt --db portfolio.db \
    --max-pages 50 --site-workers 16 --page-workers 4
```

`--page-workers` держите небольшим: это нагрузка на ОДИН чужой сайт.
Параллелить лучше по сайтам, а не по страницам одного сайта.

**Много агентств.** Одна база = один портфель. Держите базы раздельно
(`agency-a.db`, `agency-b.db`) — так проще считать, сравнивать и удалять.

**Обрыв не страшен.** Состояние каждой страницы в базе; `resume` продолжает
с места остановки. Прогон на 200 сайтов можно прервать и вернуться к нему.

## Задачи: почему их можно доверить трекеру

Одна задача = **один дефект на одном сайте**, со списком затронутых страниц
внутри. Не 6000 карточек на 200 сайтов, а десятки осмысленных работ.

Что внутри задачи: что сделать, почему это важно, где именно (список
адресов), как проверить результат.

Три решения, без которых это не работало бы на потоке:

1. **Метка аудита** (в конце описания). Повторный аудит находит по ней
   существующую задачу и обновляет её. Без метки второй прогон удвоил бы
   содержимое трекера.
2. **Дробление по предмету — избирательное.** Два раздела, отсутствующих
   в карте сайта, — две разные настройки, две задачи. А «нет H1 на восьми
   страницах» — одна работа со списком внутри.
3. **Зависимости, а не просьбы в тексте.** Если кеш отдаёт старую версию,
   правку канонического адреса нельзя проверить. Это выражено связью задач,
   которую видит таймлайн, а не фразой «сначала сделай то».

Разделы в трекере отражают срок: «Критично — сейчас», «Важно — эта неделя»,
«Средне — этот месяц».

## Что проверяется

18 правил, шесть слоёв. Порядок слоёв — это порядок работ: бессмысленно
вылизывать заголовки на странице, которая закрыта от индексации.

1. **Индексируемость** — canonical (в т.ч. на чужой язык/домен), noindex,
   разделы, отсутствующие в карте сайта.
2. **Техническое здоровье** — коды ответов, цепочки переадресаций, HTTPS,
   устаревший кеш.
3. **Языки** — объявленный язык, язык заголовка, hreflang.
4. **Контент и метаданные** — заголовок, описание, H1, дубли, пустые страницы.
5. **Скорость** — время ответа.
6. **Доступность** — изображения без описания.

Правила выросли из реальной работы над climtec.md: двуязычный сайт с
LiteSpeed, где часть дефектов не видна снаружи из-за кеша.

## Место в Imperal

Сейчас это самостоятельный инструмент на одной стандартной библиотеке
Python (без сторонних зависимостей). Дальше — приложение Imperal, и тогда
цикл замыкается:

```
аудит (читает)  →  задачи в трекере  →  правка через wp-site-connector
      ↑                                              │
      └──────────── повторный аудит подтверждает ────┘
```

Что даёт оболочка Imperal: расписание (аудит по ночам, отчёт утром),
выгрузка задач без ручного шага, и правка тех дефектов, которые коннектор
умеет исправлять сам — canonical и метаданные Rank Math.

Другие трекеры (Notion, Jira, Trello) подключаются без изменения движка:
план выгрузки общий, меняется только исполнитель.
